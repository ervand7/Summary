## 1. Core REST Principles

Resources, not actions. URLs represent nouns, HTTP methods represent operations.

```
GET    /users          # List
GET    /users/123      # Read
POST   /users          # Create
PUT    /users/123      # Replace
PATCH  /users/123      # Partial update
DELETE /users/123      # Delete
```

- `GET` is safe and idempotent.
- `PUT` and `DELETE` are idempotent.
- `POST` and `PATCH` are not necessarily idempotent.
- Use HTTP methods, status codes, and headers correctly.

Statelessness: Every request contains the necessary context. Servers should not depend on stored client sessions.

```
Authorization: Bearer <token>
```

## 2. URL Naming & Resource Design

- Use lowercase, kebab-case, plural nouns.
- Names describe business concepts, not implementation.
- Avoid verbs and ambiguous names.

```
✅ /users
✅ /payment-methods
✅ /card-transactions

❌ /getUsers
❌ /create-payment
❌ /redis-cache
❌ /data
```

Relationships: Nest resources when the relationship is meaningful.

```
GET /users/123/cards
GET /orders/123/items
```

Avoid deep nesting:

```
❌ /users/123/accounts/456/cards/789/transactions

✅ /transactions?card_id=789
```

Many-to-many: Model relationships as resources.

```
POST   /memberships
DELETE /memberships/123
```

Actions: When standard CRUD is insufficient, use sub-resources or explicit actions.

```
POST /cards/123/activation
POST /cards/123:activate
```

Long-running operations:

```
POST /verifications       # 202 Accepted
GET  /operations/123      # Check progress
```

## 3. JSON & Field Naming

Choose one naming convention and use it consistently.

- `snake_case` or `camelCase`.
- Explicit, descriptive field names.
- Booleans: `is_`, `has_`, `can_`.
- Timestamps: ISO-8601, preferably UTC.
- Enums: lowercase, stable, business-oriented.

```
{
  "user_id": "123",
  "payment_status": "approved",
  "is_active": true,
  "has_3ds": false,
  "created_at": "2025-01-01T12:00:00Z"
}
```

Avoid exposing internal implementation states.

```
❌ WAITING_FOR_PROVIDER_CALLBACK
✅ pending
```

## 4. Filtering, Sorting & Pagination

Filtering:

```
GET /transactions?status=approved&type=virtual
```

Time ranges:

```
GET /transactions?from=2025-01-01&to=2025-01-31
```

Sorting:

```
?sort=created_at
?sort=-created_at       # Descending
```

Pagination:

```
?limit=50&offset=100    # Simple, but inefficient at scale
?limit=50&cursor=abc    # Better for large/changing datasets
```

Cursor pagination generally provides more stable results when records are inserted or deleted.

## 5. HTTP Status Codes & Errors

| Code | Meaning                         |
| ---- | ------------------------------- |
| 200  | OK                              |
| 201  | Created                         |
| 202  | Accepted for processing         |
| 204  | Success, no response body       |
| 400  | Bad request                     |
| 401  | Authentication required/invalid |
| 403  | Forbidden                       |
| 404  | Not found                       |
| 409  | Conflict                        |
| 422  | Semantic/validation error       |
| 429  | Too many requests               |
| 500  | Internal server error           |
| 503  | Service unavailable             |

Structured errors: Return stable, machine-readable error codes.

```
{
  "error_code": "card_not_found",
  "message": "Card does not exist",
  "details": {
    "card_id": "123"
  }
}
```

- Never return `200` for failed operations.
- Keep error formats consistent.
- Do not expose internal stack traces.
- Treat error codes as part of the API contract.

## 6. Idempotency & Safety

Idempotency: Repeating the same request has the same intended effect as executing it once.

- `GET`, `PUT`, `DELETE` are idempotent by HTTP semantics.
- `POST` should support idempotency keys for payments and other critical operations.

```
POST /payments
Idempotency-Key: 8f9c-1234
```

Same key + same request means the server recognizes the retry and avoids duplicate processing.

Use database constraints or atomic operations to enforce idempotency safely.

## 7. Security

Authentication: Verify identity.

- OAuth 2.0 / OpenID Connect
- JWT or opaque access tokens
- mTLS for service-to-service communication when appropriate

Authorization: Verify permissions.

- RBAC (Role-Based Access Control)
- Scopes and resource ownership checks
- Prevent IDOR (accessing another user's resources)

Input validation:

- Validate types, formats, lengths, and allowed values.
- Use parameterized SQL queries.
- Never trust client-provided identifiers or permissions.

Sensitive data:

- Use HTTPS.
- Never expose secrets.
- Mask sensitive information.
- Never log passwords, tokens, or payment credentials.

## 8. API Versioning & Compatibility

Common approach: URL versioning.

```
/v1/users
/v2/users
```

- Avoid versioning individual fields (`user_name_v2`).
- Preserve existing field meanings.
- Do not remove or rename fields without a migration strategy.
- Adding optional fields is usually backward-compatible, but strict clients may break.
- Introduce a new version for incompatible changes.

## 9. Performance & Scalability

Caching:

```
Cache-Control: max-age=60
ETag: "abc123"
If-None-Match: "abc123"
```

If the resource has not changed, the server can return `304 Not Modified`.

Avoid chatty APIs:

```
❌ GET /user
❌ GET /user/profile
❌ GET /user/settings

✅ GET /user?include=profile,settings
```

Compression:

```
Accept-Encoding: gzip, br
```

Additional practices:

- Avoid N+1 database queries.
- Index frequently filtered fields.
- Use pagination for large collections.
- Cache frequently accessed data where appropriate.

## 10. Rate Limiting & Resilience

Rate limiting:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

- Limit requests per user, API key, or IP when appropriate.
- Return useful rate-limit headers.

Timeouts:

- Configure explicit request and dependency timeouts.
- Propagate cancellation and deadlines.
- Avoid waiting indefinitely.

Retries:

- Retry transient failures with exponential backoff and jitter.
- Retry only when operations are safe to repeat.

Circuit breakers:

- Stop repeatedly calling unhealthy dependencies.
- Fail fast and allow recovery checks.

## 11. Observability

Request IDs: Identify individual requests across logs.

```
X-Request-ID: abc-123
```

Distributed tracing: Track requests across multiple services.

```
traceparent: 00-<trace-id>-<span-id>-01
```

Logging and metrics:

- Structured JSON logs.
- Latency, request count, error rate.
- HTTP status distribution.
- Distributed tracing with OpenTelemetry.
- Never log secrets or sensitive payloads.

## 12. Documentation & API Contracts

Use OpenAPI / Swagger to describe:

- Endpoints and HTTP methods.
- Request/response schemas.
- Authentication requirements.
- Status codes and errors.
- Filtering, sorting, and pagination.
- Request/response examples.

Generate client SDKs and validate implementations against the contract when useful.

REST vs gRPC:

REST typically models resources:

```
POST /cards/123/activation
```

gRPC explicitly models operations:

```
rpc ActivateCard(ActivateCardRequest) returns (ActivateCardResponse);
```

## 13. Consistency & Common Mistakes

Consistency matters more than personal preference.

- One URL naming convention.
- One JSON naming convention.
- One error response format.
- Consistent pagination and filtering.
- Predictable authentication and authorization.
- Stable resource and enum names.

Avoid:

- Using `POST` for every operation.
- Returning `200` for errors.
- Deeply nested URLs.
- Exposing internal technologies or provider details.
- Breaking backward compatibility unnecessarily.
- Designing endpoints around temporary UI requirements.
- Mixing naming styles.

## 14. Interview Checklist

Before approving an API design, ask:

1. Are URLs resources and HTTP methods used correctly?
2. Are naming conventions consistent and business-oriented?
3. Are authentication, authorization, and validation enforced?
4. Are errors structured with appropriate HTTP status codes?
5. Are retries and critical operations idempotent?
6. Are filtering, sorting, and pagination scalable?
7. Are backward compatibility and versioning considered?
8. Are caching, timeouts, and rate limiting configured?
9. Are requests observable through logs, metrics, and traces?
10. Is the API documented with OpenAPI?

Key principle: Design APIs as stable contracts that clients can depend on, independently of backend
implementation details.
