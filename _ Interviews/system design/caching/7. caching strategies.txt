A caching strategy defines how reads and writes interact with the cache and database, affecting 
latency, consistency, and reliability.

### 1. Cache-Aside (Lazy Loading)
- Read: Cache → miss → DB → populate cache.
- Write: Update DB, optionally invalidate cache.
- Pros: Simple, flexible, cache failure doesn't block DB access if fallback exists.
- Cons: Cache misses, stampedes, stale data.
- Use: Most read-heavy applications.

### 2. Write-Through
- Write: Cache → synchronously persist to DB.
- Read: Usually from cache.
- Pros: Cache updated on successful writes, read-after-write consistency when correctly implemented.
- Cons: Higher write latency, cache dependency.
- Use: Read-heavy workloads requiring fresh cached data.

### 3. Write-Behind (Write-Back)
- Write: Cache → asynchronously persist to DB.
- Pros: Very fast writes, handles write bursts.
- Cons: Data loss risk, eventual consistency, complex recovery.
- Use: Write-heavy workloads where delayed persistence is acceptable.

### 4. Read-Through
- Read: Cache automatically fetches from DB on miss.
- Pros: Centralized caching logic, simpler application.
- Cons: Cache dependency, less application control.
- Use: Systems with dedicated caching infrastructure.

### 5. Explicit Invalidation
- Write: Update DB → delete affected cache keys.
- Pros: Reduces stale reads, simple to combine with TTL.
- Cons: Race conditions, missed invalidations.
- Use: Cache-aside systems requiring fresher data.

### 6. Two-Level Cache (L1 + L2)
`Application → Local Cache → Redis → DB`

- Pros: Extremely fast reads, reduced Redis/DB load.
- Cons: More complex invalidation, inconsistent local caches.
- Use: High-throughput, latency-sensitive systems.

### Interview Takeaway
- Cache-aside: Most common and flexible.
- Write-through: Consistent cache updates, slower writes.
- Write-behind: Fast writes, durability risks.
- Read-through: Cache manages DB reads.
- L1 + L2: Maximum read performance, harder consistency.
